# The DDS-bridge simulator: the real binaries against a simulated R1

`r1sim.dds_bridge` runs r1sim in REAL TIME behind the robot's own DDS interface, so the real r1mc3 binaries (`r1rt`,
`r1guard`) and r1d's clients run unchanged against it: timing-faithful integration tests, the stall and fault tests
with real processes, and operator rehearsals with the same words as on the robot. Code: `sim/r1sim/dds_bridge.py`;
the motion-switcher RPC `python/r1mc3/dds/rpc.py`; the process stack `sim/r1sim/stack.py`.

```bash
bash scripts/run.sh python -m r1sim.dds_bridge --domain 30                             # standing; until Ctrl-C
bash scripts/run.sh python -m r1sim.dds_bridge --domain 31 --stance hanging --builtin stand_lock --scene floor
bash scripts/run.sh python -m r1sim.dds_bridge --domain 32 --scene table --seconds 60 --record out/bridge.json
```

Needs the DDS extra (`uv sync --extra dds`, CycloneDDS 0.10.2: `rt/idl/build_cyclonedds.sh`). Every run uses its own
domain id on the loopback interface only (no multicast; `r1sim.stack.loopback_uri()`), so tests never meet a robot.

## What it serves (as the R1's board + Unitree's built-in controller + the Dex3 service do)

| Topic / service | Direction | What |
|---|---|---|
| `rt/lowstate` (unitree_hg LowState_) | published | the sensor model's state, the 26 joints in their hg slots, `mode_machine`, the board's 1 kHz tick, Unitree's CRC; at `--rate-hz` (500) when physics produced a new state |
| `rt/lowcmd` | applied | every sample whose CRC matches; the latest wins, whoever wrote it; held until the next (and with `--board real`, the default, released into damping 0.385 s after the last one, as our robot's board did); `mode` 0 in a slot = that motor gets zero gains; bad CRC dropped and counted |
| `rt/dex3/{left,right}/state` | published | 7 motors + the 9 x 12 pads at 100 Hz |
| `rt/dex3/{left,right}/cmd` | applied | per side, kept apart from the body command (a hand command never refreshes the body board's timeout) |
| `rt/api/motion_switcher/request` / `response` | served | CheckMode (`{"form":"0","name":"ai"}` while the built-in runs, `""` after), ReleaseMode (the built-in stops publishing) |
| the emulated built-in | published on `rt/lowcmd` | Unitree's controller as a takeover sees it, from its OWN participant at 500 Hz until ReleaseMode (`--builtin`, below) |

Every applied command is recorded (time, the writer, the smallest effective leg kp, disabled slots, CRC ok) and every
writer labelled: `builtin`, or the role in its DDS user data (`r1mc3:r1rt` / `r1mc3:r1guard`), else `w<k>`. The ground
truth (tilt, base height) is sampled at 200 Hz. These records are how the fault tests measure from the robot's side.

Wire compatibility: the hg types are generated by CycloneDDS's IDL compiler from our IDL, which regenerates Unitree's
C++ headers byte for byte; the `unitree_api` Request_ / Response_ IDL is reconstructed and regenerates Unitree's eight
headers byte for byte; QoS: writers RELIABLE + KEEP_LAST, readers BEST_EFFORT + KEEP_LAST.

## Configurations

| Option | Values |
|---|---|
| `--stance` | `centred` (standing; the built-in a stiff stand at the CoM-centred pose - Unitree's balance is NOT modelled), `hanging` (on a modelled stand, below), `9oct` (the previous controller's fall: its arm pose and IMU offset, for stall tests) |
| `--builtin` | `zero_torque` (kp 0 / kd 0 on every joint - what our robot publishes at power-on), `stand_lock` / `stand` (hanging: Unitree's fixed stand-lock preset; standing: the stand fixture), `damp`, `damp_legs`, `zero_torque_silent` (publishes nothing: a takeover is then refused - it needs a fresh built-in command to mirror), `none` |
| `--scene` | `floor` (default), `table`, or a `"package.module:attr"` builder ([`../SIMULATOR.md`](../SIMULATOR.md)) |
| `--board` | `real` (default: the identified board, [`BOARD_MODEL.md`](BOARD_MODEL.md)) or `hold` (holds the last command forever) |
| `--safety` | the least stable plausible robot: no leg / waist stiction (every stall / fall safety test runs with it) |
| `--seed` | the sensor model's seed |
| `--stand`, `--attach`, `--clearance` | hanging: the stand's geometry (the default fitted to our robot's measured hang), the attachment (`cradle` or a rigid `weld`), the feet's height |

**The stand** (`--stance hanging`): our robot hangs from the bar of a frame on its upper back, resting in a padded
cradle on a pole, the lower back against the pole, feet ~20 cm up. Modelled as two soft connect constraints at the bar's
ends (a hinge about the lateral axis; roll / yaw resisted by the bar's width), a vertical capsule (the pole) that
collides only with the frame's lower loop (a one-sided pitch stop), feet ~8 cm above the floor. The pole's position is
fitted so the model hangs at our robot's measured pitch. At construction the robot settles under the built-in's command
in lockstep, then real time starts at rest.

## Scheduled faults: `inject(kind, *, at_s=0.0, duration_s=None, every_s=None, count=None, **params)`

Windows from `at_s` after the call (wall clock), each `duration_s` long (None = until `clear(kind)`), repeated every
`every_s` s up to `count` times. `faults()` lists every window with when the bridge actually applied it.

| Kind (params) | What the peers see |
|---|---|
| `lowstate_gap` (duration_s) | no `rt/lowstate` and no hand state |
| `lowstate_drop` (fraction) / `lowstate_delay` (delay_ms) / `lowstate_crc` (fraction) | samples missing / late (a FIFO) / with a wrong CRC |
| `lowcmd_drop` (fraction) / `lowcmd_crc` (fraction) | commands lost / corrupted before the board |
| `link_down` | the motor link down both ways (the hands' USB path not affected) |
| `second_writer` (payload stand / damp / zero, rate_hz) | a foreign participant on `rt/lowcmd`; the board applies whichever wrote last |
| `motor_error` (joint, word) / `over_temp` (joint, to_c, rate_c_s) | a motor error word / a temperature ramp on one joint |
| `hand_freeze` / `dex3_death` (side) / `dex3_timeout` (timeout_s) | a hand's state repeats / stops; an opt-in hand timeout |
| `push` (impulse) | a torso impulse |
| `publisher_stall` / `cmd_reader_stall` (duration_s) | the bridge's OWN publisher / reader thread blocked (physics runs on): separates a starved simulator from starved controller processes |

## The process stack

`r1sim.stack.ProcStack` starts the bridge + `r1rt` + `r1guard` + `r1d` + `r1log` and runs the `r1` CLI one process per
word (as the operator types it); teardown kills the processes and unlinks the shared memory, never damping anything:

```python
from r1sim.stack import ProcStack
with ProcStack(domain=31, workdir=tmp, bridge={"stance": "hanging", "builtin": "stand_lock"}) as st:
    st.cli("on-stand"); st.wait_mode("on_stand", 10)
    st.cli("guard-takeover", "--stop-s", "3", "--yes")     # the guard-takeover test, as on the robot
    st.bridge.writers()                                    # who wrote rt/lowcmd, when
```

## Measured (a laptop under load)

| Quantity | Value |
|---|---|
| `rt/lowstate` published (target 500 Hz) | ~490-494 Hz, gap p99 3.0 ms; physics real-time factor ~1.0 |
| Unitree's CRC in Python | 9.5 us per LowState_ (a per-position table + numpy xor-reduce; 200 us as a plain loop) |
| the motion-switcher RPC | ~2 ms per call |
| the guard's takeover with the real processes | ~10.6 ms of board-side gap (our robot: 9.8-10.7 ms) |

## Not modelled (said plainly)

The real board's ~1 kHz state rate (500 Hz here: the Python publisher's budget); Unitree's balance (the built-in is a
stiff stand fixture); `rt/arm_sdk`; the wireless remote; the battery. Python's GIL is shared by the bridge's threads:
under heavy load the physics can fall behind real time - every result carries the real-time factor
(`log()["physics"]`). The stand's compliance is an estimate.
